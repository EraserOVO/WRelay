# WRelay

WRelay 是一个基于 NoneBot2 的 Windows 消息转发服务。当前代码包含六条相互独立的消息链路：

- Discord → QQ：实时转发和离线补发
- X/Twitter RSS → QQ：通过 RSSHub 轮询 X 账号并转发
- Bilibili RSS → QQ：通过 RSSHub 按 UP 主、标签或关键词轮询新投稿并转发
- YouTube RSS → QQ：通过 YouTube 官方频道 RSS 转发视频标题、封面和链接
- Steam → QQ：监控游戏公告、新闻和折扣，以及开发商或发行商主页所列游戏的折扣与发行状态
- QQ → QQ：授权用户通过私聊命令手动转发文字或 Discord 消息

项目不提供 QQ → Discord 自动转发，也不做双向同步。

## Windows 发布

官方 Windows 安装包目前以未签名方式发布，并附 SHA-256 校验文件。Windows 可能显示「未知发布者」或 SmartScreen 提示；校验和使用说明见[发布完整性说明](CODE_SIGNING_POLICY.md)。

五条自动链路也支持个人 QQ，通过 OneBot v11 反向 WebSocket 兼容 NapCat / SnowLuma；
不同账号可混用协议端，同一账号只允许一个连接。「设置 → 个人 QQ」管理连接及接收群。
第二期支持白名单私聊管理、明确授权的手动 QQ → QQ、Bilibili 群链接解析及定时消息。
接入及超时待确认说明见 [个人 QQ 接入](docs/PERSONAL_QQ.md)。

每个官方 Bot / 个人 QQ 的来源和转发组分别保存在 `data/bot_profiles/` 下的一份 JSON 中。
选择账号后可使用总览页文件按钮中的「导出配置 / 上传配置」跨账号快速配置；上传先对应接收群、预览，再确认合并或替换。
凭据、授权和定时计划保持原有全局管理。升级迁移、文件范围与恢复说明见 [Bot 独立配置](docs/BOT_PROFILES.md)。

## 功能

### Discord → QQ

- 实时监听已启用的 Discord 频道并转发到已启用的 QQ 群
- 支持多个 Discord 频道、多个 QQ 群和独立的 Discord 转发组
- 来源行右侧统一提供「内容筛选」、名称与来源地址编辑、移除；来源级翻译设置并入「内容筛选」，筛选项统一采用勾选框
- 多个 QQ Bot 时可在面板左上角切换 Bot 工作区，分别配置各自发现的 QQ 群目标
- 支持文字、图片、音频、文件、链接、Discord 自定义 Emoji 和 Embed 内容
- 视频附件按 Discord 原始文件发送（源站只有单一文件，不做转码或清晰度切换）；下载、超限或上传失败时省略视频且不补链接
- 支持 Discord 回复消息，转换为 QQ 可读的引用文本
- 清理 Markdown 标记，并将用户、角色、频道、`@everyone` 等提及转换为可读文本
- 支持按 Discord 用户名、关键词和消息类型筛选
- 频道与 QQ 群分别维护发送游标，避免重复转发
- 确认 QQ 已送达后写入持久回执；若进程在回执保存后、旧游标更新前退出，恢复时会跳过已确认目标并补齐游标
- 转发标题统一采用【来源 · 类型】格式并紧凑排列；Discord 标题为“【Discord】#频道 · 作者”，正文、回复引用和媒体紧随其后
- QQ 群发送失败不会影响其他群，失败群会在重试或补发时继续处理
- 失败消息会持久化到 `data/retry_pending.json`，进程重启后继续重试；媒体字节不写入队列
- 支持媒体并发下载、大小限制、发送重试、429 限流退避和链接降级
- 视频媒体以 QQ 视频消息发送；下载、超限或上传失败时跳过视频本体、不补链接（图片/音频仍降级为链接）
- Discord 或 QQ Bot 重连后自动补发离线期间的未转发消息，可限制每个频道单次补发数量
- 启用补发后后台每 60 秒检查一轮；补发发送共用至少 5 秒的间隔，并在发送前重新检查开关和群路由。单轮按每频道上限处理，剩余记录留到后续轮次。
- 补发失败按消息和目标群独立退避，从 60 秒逐步延长到最多 15 分钟；等待期间其他到期消息仍可处理，重试时间跨重启保留。
- 清空待补发时会清除当前启用群截至查询到的最新消息的缺口和延迟重试；已经进入网络发送的消息可能仍会送达。
- 补发窗口显示已登记的不同消息数、扫描状态、最近检查和简短错误；扫描未完成时数量可能增加，查询失败显示未知。
- 可选失败通知：按冷却时间向管理员反馈投递失败，避免重复刷屏
- 每条投递会记录最终结果、目标群和重试次数，供面板消息追踪查看

### X/Twitter RSS → QQ

- 通过 RSSHub 定时轮询 X/Twitter 账号
- 来源行的「内容筛选」可设置关键词、推文类型（原创/转发/引用）、消息类型（文字/图片/视频）和来源级翻译；筛选维度同时启用时取交集，旧配置中的“文件”会迁移为“视频”
- 支持原创内容、转发、引用内容、图片和视频
- 引用内容保留作者与文字，不发送被引用贴文的图片或视频；转发他人的引用贴文时也适用，主推文自身的媒体仍按消息类型筛选发送
- 视频只在成功下载时发送本体；超出媒体大小上限或下载失败时省略视频且不补链接，纯视频推文不发送。RSSHub 正常路径只有一条视频直链；回退到 X 公开时间线时取最低码率档
- 支持 RSS ETag/304 缓存，减少重复请求
- X 转发组中的群勾选控制该组内的接收状态；群还须全局启用才能参与投递，未启用时在群名称下显示提示。
- 对 RSSHub 的 429、5xx 和连接异常做同轮退避重试（最多 3 次）；其他 4xx 快速失败
- RSSHub 暂时不可用时回退到 X 公开时间线，保持订阅轮询不中断
- RSSHub 与本程序常同时开机启动：启动后 4 分钟内连接被拒视为“等待 RSSHub 启动”；X/Bilibili 遇到连接异常或等待状态时每 60 秒重试，恢复后回到配置的轮询间隔
- 使用独立的来源游标去重
- 同一推文命中多个来源时，按 X 原生推文 ID 和 QQ 接收群跨来源去重；最近 90 天内已确认送达的群不会重复收到
- 管理面板可配置投递保护：默认最短发送间隔 5 秒、每小时最多 300 条、每个来源积压上限 100 条；限速按所有 X 来源合计，积压队列持久保存并在后台逐条发送
- QQ 未连接、发送失败或媒体处理失败时保留游标和队列条目，连接恢复后继续补投
- 管理面板提供 RSS 运行状态、最近轮询结果、积压数量和失败原因
- 来源筛选可设置自动转发消息类型（文字/图片/视频）；与关键词及推文类型同时设置时取交集，消息类型会控制是否发送媒体

### Bilibili RSS → QQ

- 通过 RSSHub 轮询 Bilibili 新投稿
- 支持按 UP 主 UID、Bilibili 标签或关键词注册来源
- 支持多个来源和独立的 Bilibili 转发组，可分别选择 QQ 接收群
- 同一投稿命中多个来源时，按 Bilibili 投稿 ID 和 QQ 接收群跨来源去重；最近 90 天内已确认送达的群不会重复收到
- Bilibili 来源注册只选择 UP 主 UID、标签或关键词范围并填写地址；加入转发组后可编辑显示名称与来源地址
- 来源行的「内容筛选」可设置关键词、投稿类型、消息类型和来源级翻译；各筛选维度同时设置时取交集
- 支持可调的最短发送间隔、每小时上限和每来源积压上限；积压超限可选择保留最新或保留最旧
- 限速队列持久化保存，RSS 突发投稿不会在一次轮询中集中发送；Bilibili RSS 请求按来源串行访问，并对 429/5xx/连接异常做退避重试
- Bilibili 标签/关键词 RSSHub 路由以及 UP 主动态路由可能依赖 Chromium 或有效的 `BILIBILI_COOKIE_1`；上游 412 通常会被 RSSHub 转成 503
- 消息统一使用【来源 · 类型】标题并紧凑排列；Bilibili 格式为“【Bilibili · 投稿】[UP 主名称]”，优先使用投稿作者，缺失时回退到注册来源；按筛选发送标题、投稿地址、封面和视频本体，不发送标签、简介及播放统计
- 消息类型筛选勾选“视频”时即尝试从 Bilibili 播放接口获取 360P 单段视频本体；接口未返回 360P、视频多段、超过媒体大小上限（默认 30 MiB）或下载失败时只省略视频本体，不补发 CDN 地址或投稿页链接；不勾选“视频”则不尝试视频本体
- 私聊手动转发统一在「QQ → QQ」页的紧凑「手动转发」卡管理：「已注册来源」按钮打开弹窗，用 Discord / X / Bilibili 三个 Tab 分别查看已注册频道/账号/来源；右下角「内容筛选」对三链路各自独立设置消息类型筛选。视频本体按“视频”类别控制（旧配置里的“文件”会自动迁移为“视频”）
- 手动转发引用的内容（未引用时取最近一条消息）可以是投稿视频、专栏或动态链接（专栏与动态共用 `bilibili.com/opus/{id}`，也支持 `/dynamic/{id}` 与 b23.tv 短链接）。专栏发送标题、简介摘要、封面和专栏地址；动态发送正文文字、封面和动态地址；视频仅转发 360P 单段本体，拿不到时只发送其他已勾选组件，不补发链接，仅勾选「视频」时静默不回复
- 首次启用来源或 QQ 群时建立游标基线；UP 主专栏/动态 feed 首次启用时也分别建立基线，不批量刷出 RSS 历史
- RSSHub 暂时不可用、QQ 未连接或发送失败时不推进游标，恢复后继续补投
- 与 X 链路相同：启动后 4 分钟内 RSSHub 连接被拒视为“等待 RSSHub 启动”；连接异常或等待状态时每 60 秒重试，恢复后回到配置的轮询间隔

### Steam → QQ

- 在「Steam → QQ」页面添加游戏 AppID / 商店地址，或添加开发商、发行商的 Steam 商店主页；选择监控内容，并在 Steam 转发组中选择来源和已启用的 QQ 接收群。
- Steam 来源行与其他链路一致，提供「内容筛选」、名称与来源地址编辑、移除；事件类型、DLC/捆绑包、新闻 feed 和翻译选项在「内容筛选」中设置
- 可按来源启用自动翻译并选择是否保留原文；翻译使用共享自动翻译服务路由，失败时继续发送原文
- 游戏来源支持新公告、新闻与折扣；新闻可按 Steam feed 名称筛选。开发商或发行商来源监控其主页关联游戏的折扣、新公开商店页面和发行状态变化（抢先体验开售、正式发售、抢先体验转正式版）。社区讨论帖不属于来源范围。
- Steam 官方新闻接口与公告 RSS 提供消息。部分游戏的公告 RSS 可能不可用，此时使用新闻接口的官方公告来源；新闻接口暂不可用时继续检查 RSS，并保留游标以便恢复后补查。两种来源的同标题、同发布时间公告按游戏去重。
- 商店地区默认 CN，可设置两位国家代码；价格、币种和可见游戏依 Steam 对该地区的返回为准。默认监控游戏本体，可按来源选择包含 DLC 和捆绑包折扣；价格未知时保留上次成功记录。捆绑包价格按未登录账号的商店数据展示，实际价格可能因已拥有的商品而不同。发行商或开发商来源仅在 Steam 数据能确认对应归属时监控捆绑包，无法确认的项目会显示错误。
- 开发商/发行商游戏列表和商店详情使用 Steam 商店未正式文档化的数据接口，可能变化或遗漏；主页未关联、隐藏或地区不可见的游戏无法保证发现。扫描大量游戏需要逐个请求，状态变化可能延迟。消息、价格及状态只在轮询时检查，短暂出现又结束的折扣可能错过。新闻补查单轮最多读取 1,000 条；超出时暂停该来源并保留游标，状态卡显示错误。
- 来源或目标群首次启用时建立基线。消息、价格与发行状态的变化进入按账号保存的持久队列；每个群独立记录发送结果。队列达到上限时暂停推进受影响的状态，待发送后重试。暂时关闭来源、事件或目标群会暂停对应队列，重新启用后继续处理。
- 轮询间隔、最短发送间隔、每小时发送上限及队列上限可配置；Steam 请求优先使用「网络代理」中设置的 Steam 专用代理。留空时先直连，遇到连接失败、超时或服务器提前断开时尝试已配置的 Discord 代理。Steam 返回 HTTP 429 时按 `Retry-After` 退避。面板显示首轮检查、扫描进度、最近检查、待发送与暂停数量及来源错误；可在确认后清理因来源、监控内容或目标群停用或移除而暂停的消息。启用高级运行状态备份时包含 Steam 基线和队列。

### YouTube RSS → QQ

- 优先通过 YouTube 官方频道 RSS（`feeds/videos.xml`）轮询新视频；RSS 请求失败时尝试读取频道视频页和视频发布时间，不需要 RSSHub，也不需要 YouTube API Key。后备读取依赖 YouTube 页面结构，并会增加页面请求
- 支持频道 ID（`UC` 开头）、`@handle` 或直接粘贴频道主页地址注册来源；`@handle` 首次轮询时解析并缓存频道 ID，RSS 返回 HTTP 404 时会短暂重试并重新解析一次，若 ID 已变化则用新 ID 重试
- 第一期只转发视频标题、封面和视频链接，不下载或上传视频本体，不提供关键词搜索来源和 YouTube 手动转发
- 支持多个来源和独立的 YouTube 转发组，可分别选择 QQ 接收群；每个来源可单独设置关键词、消息类型（文字/图片/链接）和翻译，翻译选项位于「内容筛选」中
- 消息统一使用【来源 · 类型】标题并紧凑排列；YouTube 格式为“【YouTube · 视频】[频道名称]”，随后发送标题、视频地址和封面
- 支持 RSS ETag/304 缓存；对 429、5xx、连接异常和超时做退避重试，多个来源的请求保持间隔并限制并发。直连或本机代理连接失败、超时时，可通过不同且正在监听的 Windows 系统代理再试一次
- 首次启用来源或 QQ 群时建立游标基线，不批量补发频道历史视频
- 投递保护默认最短发送间隔 60 秒、每小时最多 10 条、每来源积压上限 10 条；超限可选择保留最新或保留最旧，积压队列持久保存
- 状态卡显示本轮完成数量及最近最多三个频道的检查结果。整轮结束后更新轮询时间、发现、发送和失败统计，状态接口还记录各来源连续失败次数；队列或状态文件损坏时暂停自动投递并保留原文件
- YouTube Data API Key 可作为频道上传主读取源，RSS 保留备用；可通过 YouTube 页右上角钥匙按钮或「设置 → 机器人与服务」填写并保存，界面不回显 Key，保存后自动重启；YouTube 可单独配置 `YOUTUBE_PROXY`，未配置时沿用 `DISCORD_PROXY` 或系统 TUN 路由

### Bilibili 自动解析

- 默认关闭，在「Bilibili」页转发组卡片下方的「自动解析」卡片开启；只对已登记且启用、且属于当前 Bot 的 QQ 群生效，不新增群选择器
- 群成员发送 Bilibili 投稿视频链接（`bilibili.com/video/BV…`、`av…`，支持 `?p=` 分 P）或 `b23.tv` / `bili2233.cn` 短链时，机器人取消息中第一个 Bilibili 链接，跟随短链重定向后下载 360P 视频本体，并以被动回复把视频文件发回同一个群
- 下载失败、接口未返回 360P、超过媒体大小上限（默认 30 MiB）或视频不是单段时静默跳过，不再回复提示或原链接；直播、番剧、专栏、动态和其他站点链接同样静默，不发错误消息
- 同一群内同一视频（按投稿编号与分 P）10 分钟内只发送一次，并有在途去重避免并发重复下载
- 机器人自己发送的消息、以 `/` 开头的命令、@ 机器人的消息和私聊消息都不触发；群聊的 @ 提示只针对单独 @机器人，@机器人时附带的链接不会被解析
- 前提是群管理员在机器人资料页开启「接收所有消息」，否则普通群消息不会推送给机器人，本功能收不到任何链接
- QQ 小程序分享卡片依赖适配器保留的 `ark_data`，当前版本不支持

### 图片化转发

Discord、X、Bilibili、YouTube、Steam 自动投递与授权 QQ 手动转发共用「图片化转发」总开关。任一链路的「内容筛选 → 消息呈现」保存后，同步应用到所有账号的频道与来源。默认开启深色卡片，勾选旁边的「浅色模式」切换浅色，关闭图片化后隐藏主题选项。
卡片按现有筛选和翻译设置呈现正文、引用和图片。Discord 自定义表情按原顺序排入文字，动态表情取第一帧。保留原文时译文在上、原文在下。卡片高度随内容变化，过长时分图，有有效来源地址时在最后一张附链接和二维码。
视频、语音及文件仍按链路原有规则处理。卡片先发，符合条件的视频作为独立 QQ 视频发送。纯视频、无法生成卡片或内容超过渲染上限时使用普通格式。

### 自动翻译

- 「QQ → QQ」页提供一张共享「自动翻译」卡片：首选与后备服务由全项目共用；卡片左下角的「翻译链路」按钮打开二级窗口，窗口内六个整行开关（链路名在左、轨道在右，外围无描边或常态底色）分别批量启用或关闭 Discord → QQ、X/Twitter RSS → QQ、Bilibili RSS → QQ、YouTube RSS → QQ、Steam → QQ 与 QQ 手动转发的翻译，点击后立即保存
- 新增 Discord、X、YouTube 和 Steam 来源默认开启翻译，新增 Bilibili 来源及 QQ 手动转发默认关闭；已有来源和手动开关的设置保持不变。没有来源时，链路开关显示新来源的默认状态，添加来源后才能批量切换。
- Discord 频道、X 账号、Bilibili 来源、YouTube 频道和 Steam 来源可在各自来源行的「内容筛选」中设置是否翻译及是否保留原文；Discord、X、Bilibili 和 YouTube 还可设置是否显示时间。「翻译链路」中的链路开关用于批量启用或关闭对应自动链路的来源翻译
- 支持腾讯 TMT、OpenAI 兼容 AI API 与本机 Ollama（loopback:11434，适用于 Qwen 等本地模型）；所有翻译服务失败时仍发送原文
- 「翻译服务配置」里的模型列表按拖动顺序组成 AI 首选与备用链；请求失败（包括超时或空响应）时依次尝试下一项，全部配置模型失败后仍保留符合条件的服务端模型目录兜底
- 面板模型列表将最近一次真实翻译成功使用的模型标为「工作中」，其他模型显示各自最近的 AI 检测状态；模型配置字段可折叠并通过点击列表项切换编辑
- 模型列表为每项显示最近检测状态和状态灯；「检测当前 API」更新对应项，「检测全部 API」按优先级逐项更新；检测结果不包含 API 地址或密钥

### QQ 手动转发

授权 QQ 用户可以使用：

```text
/定时消息                       查询定时消息状态
/定时消息 <开启/关闭/清空>       管理定时消息
/转发 列表                      查看可转发目标群与转发方法
/私聊转发                       私聊查看同一份名单（与 /转发 列表 相同）
/转发 1 3                       把引用消息转发到第 1、3 个群
/转发 全部                      私聊转发到全部已启用群（群聊无此项）
/注册                           点击菜单按钮即可提交用户注册申请
/菜单                           查看菜单
```

使用 QQ 自带的“回复”引用一条消息，再发送 `/转发 序号`（可一次写多个、可重复序号），机器人直接把被引用的内容转发到目标群并回复一次结果。没有引用时使用该用户最近一条普通消息（600 秒内），因此也可以先发内容再发命令；普通文字消息仍会收到「未知命令」提示，这是正常现象，不影响缓存；直接发送 Discord / X / Bilibili 链接时只缓存为待转发内容，不再回复「未知命令」。目标名单为纯文本编号，不提供按钮；群聊目标限定为与当前群同属至少一个 QQ 转发组的其他已登记群，私聊目标是全部已启用群。

引用的内容可以是文字和图片/附件。若内容本身是 Discord 消息链接、X/Twitter 状态链接或 Bilibili 链接（投稿视频、专栏、动态，含 b23.tv 短链接），WRelay 会抓取对应内容并复用媒体发送逻辑；Discord、X、Bilibili 的视频都只发送视频本体，超出媒体大小上限、下载或上传失败时省略视频且不补链接（Bilibili 视频还要求 360P 单段，视频分段时同样省略）；专栏和动态发送标题或正文、封面与对应页面地址。机器人消息和命令消息不会被转发。「QQ → QQ」页的紧凑「手动转发」卡左下角「已注册来源」按钮用 Discord / X / Bilibili 三个 Tab 分别查看各链路已注册频道/账号/来源，右下角「内容筛选」分别配置各链路手动转发的消息类型筛选（X 支持文字、图片、视频，Bilibili 支持文字、图片、链接、视频，窗口内只显示该链路可用的筛选项）。三类链路共用同一套已授权 QQ 用户白名单。

转发消息使用【来源 · 类型】标题并紧凑排列。群聊 QQ→QQ 手动转发以“【QQ 转发 · 群名】”标注来源群，后接正文，不插入空行。含图片时先发送来源与正文的文字消息，再单独发送图片，避免 QQ 客户端将图片显示在正文前；纯文字转发仍在同一条消息中。

### QQ 权限与注册审核

- 自动记录发现的 QQ 用户 OpenID 和群 OpenID
- 私聊点击菜单中的“提交用户注册”按钮，或发送 `/注册`，即可提交用户注册申请
- 在群内 @机器人发送 `/注册群`，即可提交当前群注册申请；群聊不再展示独立菜单，`/菜单` 与单独 @机器人（不附带其它内容）显示当前群可转发目标列表
- 每条注册申请会收到固定的 8 位申请识别码（格式 `XXXX-XXXX`）；请把识别码转给管理员，用于在审核列表中对应申请。识别码只用于核对，不代表授权。
- 已登记的群不能重复申请；待审核群再次提交时会返回原识别码。用户注册同样去重：已在 `qq_user_openids` 登记的用户再次发送 `/注册` 会提示“已经登记、无需重复申请”，待审核用户再次提交会返回原识别码。管理员可在注册审核列表粘贴识别码，筛选并定位对应申请。
- 注册申请按当前 QQ 用户/群 OpenID 绑定，不要求提供 QQ 号、昵称、群号或群名称；可选地附加完整资料以便审核时查看
- 私聊发送未知斜杠命令或普通文字时，会提示“该命令未知，点击下方按钮展开菜单：”并附菜单按钮（已授权用户的普通文字同时会缓存为最近转发内容；直接发送 Discord / X / Bilibili 链接时只缓存，不回复该提示）；群聊只有 `/菜单` 和单独 @机器人（不附带文字、附件或引用）会显示当前群可转发目标列表，@机器人后带内容、@其他成员、普通聊天和未知斜杠命令都不回复
- 管理员可在面板审核用户和群注册申请
- 审核通过只会加入配置，默认仍为禁用状态，必须由管理员手动启用
- 保存用户昵称、群名、账号和最后活动时间，供管理面板展示
- 身份资料与权限列表分开保存，身份识别不会自动授权

### QQ 私聊管理命令

私聊 `/菜单` 为手机常用操作提供运行状态、手动转发、定时消息、注册申请和重启五个入口。「手动转发」打开纯文本目标群名单与转发方法（同 `/转发 列表`，见上文）。注册申请入口可查看用户/群待审核申请，也可提交用户注册申请。自动转发组、Bot 账号、QQ群、权限用户和离线补发等低频命令不再列入主菜单。离线补发默认由后台自动执行，管理面板不提供单独管理入口；需要时仍可使用下方 QQ 私聊命令查看或操作。私聊发送未知斜杠命令时，除「展开菜单」外还会附一个以该命令原文为动作的按钮（enter 模式），误点只会重发同一条未知命令。群聊不显示独立菜单：发送 `/菜单` 或单独 @机器人（不附带文字、附件或引用）会显示当前群可转发目标列表，其他群消息一律不回复；群注册仍通过 `/注册群` 提交。

授权用户可以使用：

```text
/运行状态                       查看机器人状态和统计
/群列表                         查看 QQ 群列表
/频道列表                       查看 Discord 频道列表
/权限列表                       查看私聊权限列表
/补发状态                       查看离线补发状态
/补发状态 开启/关闭             开关离线补发
/补发状态 执行/清空/刷新        触发、清除或刷新补发状态
/定时消息                       查看定时消息状态
/定时消息 清空                 清空定时消息
/重启                           重启机器人
/菜单                           查看菜单
```

这些管理命令需要桌面管理进程运行；窗口收起到托盘时仍可使用，退出桌面端后暂不可用。转发机器人本身可继续运行。

私聊 `/菜单` 会返回标题为“WRelay菜单”的按钮面板，菜单本身不包含再次打开菜单的按钮；按钮标签使用纯文字，不添加 emoji 或装饰符号。私聊菜单提供运行状态、手动转发、定时消息、注册申请和重启入口；「手动转发」打开纯文本目标群名单与转发方法。私聊发送未知命令时会提示“该命令未知，点击下方按钮展开菜单：”并附菜单按钮，另附一个以该未知命令原文为动作的按钮。群聊没有独立菜单；群聊发送 `/菜单` 或单独 @机器人（不附带文字、附件或引用）才显示当前群可转发目标列表。按钮点击后自动发送对应中文斜杠命令并直接收到结果，不需要再点发送键；`/定时消息` 的查询结果下方附带开/关/清空按钮；转发名单不再提供按钮，转发时由用户引用消息后直接发送 `/转发 序号`。命令结果及按钮触发的后续回复使用 Markdown 一级标题，替代原来的方括号标题；按钮发送失败时仍优先保留标题样式。按钮使用 QQ 客户端 8983+ 的自动发送特性，旧版本会退化为把命令填入输入框（仍可用）；命令解析与权限校验与手输命令一致。按钮类型由 `QQ_BUTTON_MODE` 控制：默认 `enter`（指令按钮自动发送，聊天里会多出一条命令消息）；`callback`（回调按钮，点击后机器人直接回复、用户不产生消息）实测在 WebSocket 接入下点击会提示「请求第三方失败」，只在开放平台接入方式为 Webhook 时可用。

### Windows 桌面管理程序

桌面端主页面、表格及二级窗口的图标按钮统一使用 MingCute Icons；有圆角矩形底或边框的图标按钮保持正方形。总览机器人状态卡与链路页共用横向状态行，并在进程操作组左侧显示分隔线。具体图标映射和尺寸规则见 [界面设计说明](docs/DESIGN.md)。

界面沿用深色风格，导航图标与“打开”按钮使用统一尺寸。网页配置、诊断、备份等二级窗口共用分级宽度、固定标题/操作栏和内部滚动区，正文统一按网格起排、底栏按钮左右分区、开关使用胶囊样式；具体规范见 [界面设计说明](docs/DESIGN.md)。Windows 原生系统对话框保留系统样式。

桌面窗口通过 WebView2 加载本地页面，管理操作在桌面进程内执行，不再监听 `18090`。机器人自身的本机 `18082` 接口继续提供运行状态与补发等能力；QQ 私聊管理命令通过 Windows 本机管道与桌面进程通信。桌面端提供：

- 启动、停止、重启机器人
- 机器人异常退出后的自动拉起
- Windows 开机自启
- 管理 Discord 频道、X/Bilibili/YouTube 来源、QQ 接收群和私聊权限（QQ 接收群与授权用户并排显示在「QQ → QQ」页转发组中）
- 创建、重命名、排序和删除 Discord、X、Bilibili、YouTube、QQ→QQ 转发组；每个页面最多 30 组，空组删除无需确认，有成员的组删除需确认，删除后选中前一组
- 配置频道筛选条件
- 注册新的可读 Discord 频道、X 来源、Bilibili 来源和 YouTube 频道
- 审核 QQ 用户/群注册申请
- 配置腾讯 TMT、AI API 和自动翻译路由，在模型列表查看当前工作状态与检测结果
- 查看频道权限审计结果和真实频道名称
- 查看、清空和动态切换机器人日志级别
- 查看转发统计
- 导出和恢复配置备份（ZIP 及解压内容上限 32 MB）；可选包含游标、重试队列、X/Bilibili/YouTube 队列与来源状态及跨来源去重记录，恢复运行状态前需停止机器人，系统会自动保存回退快照
- 后台自动扫描并补发 Discord 离线期间的消息（默认开启，无需在面板配置）
- 查看 X RSS、Bilibili RSS 和 YouTube RSS 轮询状态
- 编辑 QQ 定时消息：主面板「＋ 新增」打开仅含一条空白消息的编辑器，保存后追加到当前组；消息行的编辑和删除只作用于该条消息。接收群由消息组统一指定
- 在“设置 → 启动与维护 → 运行日志”窗口中打开消息追踪二级窗口，查看最近 50 条投递结果
- 使用连接诊断工具查看机器人、Discord、QQ 和待重试投递状态
- 在 QQ → QQ 页面机器人状态卡片中开关失败通知；设置页的失败通知开关与其同步
- 编辑 QQ Bot 与 Discord Bot 配置
- 多个 QQ Bot 时通过左上角 QQ Bot 下拉框切换当前工作区；总览与各链路页按当前账号显示数量，频道/来源只统计连到启用转发组和启用接收群的项目，RSS 状态、统计和待重试数量也按当前账号显示；Discord → QQ 与 X → QQ 页面只显示该 Bot 的目标群，机器人进程与 PID 由所有账号共享
- 桌面窗口使用 38px 自定义 Windows 标题栏，保留系统缩放、双击最大化/还原和 Snap；窗口按钮统一尺寸，关闭悬停显示红色；窗口位置、尺寸及最大化状态会保存在 `data/desktop_window.json`，并在显示器变化后回到可见区域。应用图标、托盘与 Windows 快捷方式统一使用 WRelay 主标识；侧栏有 8 个导航入口，总览保留 5 张链路卡，Steam 状态在 Steam 页面查看。

桌面程序每次启动均进入运行总览，集中查看机器人状态、各转发链路状态与配置数量，并可直接进入 Discord → QQ、X → QQ、YouTube → QQ、Bilibili → QQ、QQ → QQ 管理页。设置页按“应用、外观与窗口、机器人与服务、启动与维护”四个 Card 组织，统一使用左侧说明、右侧控件的设置行，开关为 32×18 裸轨道（外围无按钮底色或描边）；“外观与窗口”可切换主题和渐变扫光动画，扫光显示在正常运行的状态卡、当前选中且启用的转发组标签，以及开启时的“界面动画”设置行；机器人状态卡正常运行时使用与“运行中”徽标相同色相的绿色扫光，浅色主题提高扫光明度，开启中的“界面动画”设置行也使用绿色扫光。连接任务进行中不触发红色失败光，确认连接失败时才显示每 4 秒循环的红色呼吸光。重启按钮在机器人停止时仍保留在原位并置灰禁用，可用时图标使用深灰色。开发实测口令：wrelayreminder 预览维护提醒，wrelayfail 切换失败光效，wrelayclear 清除测试预览。设置还提供当前版本和 GitHub 稳定版更新检查：“应用”卡片中可开关“自动检查更新”（默认开启，启动后自动检查一次）；发现新版本后“检查更新”按钮变为“立即更新”，点击后下载官方安装包并显示进度百分比与当前步骤，随后启动安装向导由用户确认安装，不会静默替换正在运行的程序。机器人凭据、翻译服务、开机自启、失败通知、备份恢复、连接诊断、重启管理程序、配置向导和问题反馈统一从设置页进入。配置表会按可用宽度调整列，长 ID 使用省略号、悬停查看完整值并提供复制按钮；窄窗口会收起为图标导航并调整为单栏布局。桌面窗口使用自定义标题栏、原生缩放边框与系统 Snap；位置、尺寸和最大化状态保存在 `data/desktop_window.json`，如果上次显示器不可用则重新放到当前可用屏幕。关闭窗口默认隐藏到托盘，也可在设置选择“退出桌面端”或“每次询问”；偏好保存于 `data/desktop_preferences.json`，立即生效，普通关闭/退出均不停止机器人。托盘右键打开与主界面主题一致的自定义浮窗，可打开窗口、进入总览/设置、按运行状态启动/停止/重启，以及退出桌面端或执行需确认的“停止机器人并退出…”。左键双击仍打开主窗口；退出桌面端后不再保留托盘与看护。管理页面仅在桌面窗口中打开。全局运行日志统一从“设置 → 启动与维护 → 运行日志”打开；使用标准二级窗口，等宽控制台最高 320px 并内部滚动，级别、自动滚动和消息追踪位于正文下方同一行；底栏两侧分别为复制日志和清空日志。五个转发页不再显示日志卡片。根文档预留稳定滚动条空间，避免切页与折叠时宽度跳动。机器人启动、停止和重启的主入口为“总览 → 机器人状态”，托盘提供同功能快捷入口：运行时显示停止/重启，停止时显示启动。五个功能页不再提供机器人启停工具或重复日志入口；QQ → QQ 页保留失败通知快捷开关。布局参考见 [docs/DESIGN.md](docs/DESIGN.md)。
桌面端五个转发页采用“机器人状态栏 → 转发组”布局。Discord 离线补发在后台默认自动运行，不再在管理面板显示状态卡片、详情窗口或手动操作按钮；RSS 与 Steam 状态仍可通过顶部状态入口打开详情。YouTube 二级状态窗口还提供不回显的 Data API Key 输入与保存，保存后自动重启机器人。QQ → QQ 页在最右侧按钮槽提供失败通知图标开关，其余操作槽保持预留。其余页面卡片继续遵循两列网格与统一尺寸规则。

## 快速开始（Windows）

当前安装脚本和桌面程序仅支持 Windows。正式安装包提供带 WRelay 名称和图标的可执行程序，目标电脑无需预装 Python；源码运行需要 Python 3.11 及以上。安装包会在缺少 WebView2 Runtime 时安装该组件。

1. 正式安装包使用编译后的 `WRelay.exe` 桌面程序和 `WRelay.Bot.exe` 机器人程序，安装时从 `.env.example` 生成 `.env.prod`；源码目录运行 `install.bat` 时，如果没有内置 Python，则创建 `.venv` 并安装项目依赖。

   安全依赖已锁定为 `cryptography==50.0.1`、`multidict==6.9.1`，QQ 适配器使用仅修改依赖元数据的本地兼容补丁。
   源码安装需完整保留 `vendor/` 并使用 `pip install -r requirements-lock.txt -e .`；Windows 需使用 64 位 Python。
   现有安装包用户需安装重新构建的版本，单独更新仓库不会替换已安装的运行时。详见 [补丁来源与验证](vendor/README.md)。
2. 源码版本如果不存在 `.env.prod`，安装脚本会从 `.env.example` 生成配置模板。
3. 双击 `启动面板.bat`，打开 WRelay 桌面窗口；安装包用户可用桌面或开始菜单快捷方式。
4. 全新未配置时会显示首次配置向导；已有用户可从「设置 → 应用 → 配置向导」进入。先选择 Discord、X、Bilibili 或 QQ 授权私聊转发，再按步骤填写所需账号、检查连接、审核并授权用户、选择接收群和来源，最后确认启用。
5. 账号基础配置可直接在界面完成。QQ 账号为共同必需项；只有使用 Discord 时才需要 Discord Token。需要本地 HTTP 代理时，可在 `.env.prod` 配置 `DISCORD_PROXY`；账号仍由向导保存，再由用户点击「启动／重启并检查」使其生效。
6. Discord 需要本机网络可访问；`DISCORD_PROXY` 用于 Discord API、Gateway、Discord 托管媒体和 X/Twitter 媒体 CDN（`pbs.twimg.com`、`video.twimg.com`）；YouTube 请求可由 `YOUTUBE_PROXY` 单独覆盖，未设置时沿用 `DISCORD_PROXY` 或系统虚拟网卡（TUN）。程序会清理通用代理环境变量，不通过 `HTTP_PROXY` 指定本地端口；同时会移除系统代理绕过列表中的方括号 IPv6 条目（如 `[::1]`），避免 httpx 把 `:1]` 当成非法端口而中断 QQ/Discord 连接。若 `DISCORD_PROXY` 的本机端口已失效，启动时会自动跟随 Windows 系统代理的当前端口；Discord 网关在启动后约 24 分钟内按退避持续重试，每次重试前都会复查代理端口。X/Bilibili 需要可访问的 RSSHub 服务，向导可检测来源，但不会安装 RSSHub；YouTube 可通过 YouTube 页右上角钥匙按钮或「设置 → 机器人与服务」填写 `YOUTUBE_DATA_API_KEY` 启用官方 Data API 主源，RSS 作为备用，不需要 RSSHub；第一期不在配置向导中提供 YouTube 搜索来源，请在桌面端「YouTube → QQ」页注册频道。

向导沿用桌面端深浅主题和公共二级窗口样式，支持上一步、稍后配置和从设置恢复进度。进度保存在 `data/onboarding.json`，不包含密钥；账号仍由原凭据文件保存。已注册来源和群会复用，重复确认不会重复创建同一转发组。审核不会自动授权，用户授权和群启用均需明确操作。

结果页区分配置保存、连接状态和投递记录；向导不自动向群发送测试消息，按页面说明主动验证。QQ 分支引导现有授权私聊流程，授权范围仍是全局白名单与已启用接收群，不创建群聊互转规则。

详细的 Bot 创建、权限、`group_openid`、频道登记、代理和 RSSHub 配置方式见 [docs/SETUP.md](docs/SETUP.md)。

## 配置与权限说明

- Discord 频道、X/Bilibili/YouTube 来源、QQ 群和 QQ 用户是否启用，以 `data/settings.json` 为准。
- Discord、X、Bilibili 和 YouTube 分别使用独立的转发组配置；全局启用和转发组成员关系必须同时满足，消息才会发送。
- QQ 官方机器人使用 `group_openid`，不能从普通群号直接推算；同一个实体群被多个 Bot 发现时，
  每个 Bot 会保存自己的 OpenID 和转发目标关系。
- 旧配置中没有 Bot 归属的群继续由第一个已连接 QQ Bot 处理；面板状态卡片会显示当前工作区的连接状态。
- 自动发现 OpenID 只负责记录，不会自动授权。
- `.env.prod` 包含机器人密钥，请勿提交或外传。
- 公域 QQ 机器人可能受到主动消息权限、时段和频率限制。

## 运行数据

主要运行时文件包括：

- `data/discord_gaps.sqlite3`：Discord 投递缺口、扫描起点和已处理记录；定期或手动补发时处理当前启用目标的缺口，停用目标的记录保留，已扫描范围的已处理记录会清理。
- `data/settings.json`：频道、来源、群、用户、转发组和补发配置
- `data/discord_last.json`：Discord/X/Bilibili/YouTube/Steam 按目标群保存的去重游标
- `data/bilibili.json`：Bilibili RSS 的 ETag 和轮询缓存
- `data/youtube.json`：YouTube 来源的频道 ID 缓存、ETag 和轮询状态
- `data/x_protection.json`：X 投递保护的限速窗口和待发送积压
- `data/bilibili_protection.json`：Bilibili 限速时间窗、待发送积压和延后跳过记录
- `data/youtube_protection.json`：YouTube 限速时间窗、待发送积压和延后跳过记录
- `data/stats.json`：成功、失败和当日转发统计
- `data/message_trace.json`：最近投递结果追踪（自动限制保留数量）
- `data/qq_identities.json`：QQ 用户和群身份资料
- `data/qq_registrations.json`：待审核注册申请
- `data/channels_audit.json`：Discord 频道权限审计结果
- `data/logs/bot.log`：机器人运行日志

这些文件属于运行时数据，不应提交到版本库。

## 长期运行与自动维护

从 0.1.1 起，桌面管理程序默认每小时创建一份经过校验的备份，保留最近 30 份，保存到
`data/auto_backups/`。在「设置 → 启动与维护 → 备份与维护」可查看告警、关闭自动备份、
立即备份或恢复所选有效备份。恢复会先校验、保存恢复前副本，暂时停止机器人；成功后按操作前状态启动。
备份包含面板配置、游标、重试队列、Discord 补发数据库、X/Bilibili/YouTube 队列与来源状态及投递去重数据库，不含账号密钥。备份受 32 MB 限制，数据库快照会移除空闲页；数据超过限制时会告警并保留旧备份。恢复不含 Discord 补发数据库的旧版游标备份时会重建空补发数据库，恢复前数据库保存在回退备份中。
恢复旧运行状态可能产生重复投递或漏发，因此需要在界面确认；不会静默回滚配置或自动清空损坏队列。

同一 RSS 来源连续三轮失败、队列/游标文件损坏和自动备份失败会显示维护告警；开启失败通知后，账号专属告警由 Bot API 按告警 ID 锁定到对应 Bot，并只发送给该 Bot 已启用的授权用户；无法确认归属时不会广播。尚未迁移到独立账号配置的旧版 RSS 来源仍按共享来源处理；共享配置、数据库和备份错误发送给所有配置 Bot 的授权用户。QQ 不可用时无法通过 QQ 通知，恢复连接后再尝试。
独立的 `WRelay.Guardian.exe` 看护桌面管理进程：异常退出或管理接口连续 2 分钟无响应时，等待 30 秒后
恢复到托盘并保留机器人运行意图。正常退出/重启会结束旧看护；10 分钟内最多自动恢复 5 次，避免无限重启。
电脑关机、休眠、退出 Windows 登录或整个进程树被结束时不能继续工作。

请开启开机自启，保留桌面端在托盘，保持电脑通电联网；本机自动备份不能替代异地备份。
